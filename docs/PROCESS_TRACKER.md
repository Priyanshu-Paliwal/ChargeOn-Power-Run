**Desert_field.glb was the hard problem of this milestone.** Standard `simplify()` plateaued at ~40% reduction no matter how loose the error tolerance (tested 0.02 through 1.0 — no meaningful difference). Root-caused (not guessed) via a union-find pass over the index buffer: the raw scan has 900+ disconnected geometry islands, and `simplify()`'s topological border-locking — which protects every one of those island boundaries — isn't governed by the error/ratio budget at all, so no amount of loosening it helped. Fix: decimate with meshoptimizer's `simplifySloppy()` called directly on raw position/index buffers instead of the attribute-aware wrapper — it has no concept of "island borders" to protect. Result: 299 MB → 1.46 MB (down to 38,880 verts, bounds/footprint confirmed unchanged, zero non-finite positions).

**One small necessary code change outside "assets only" scope**: `Engine.js`'s `loadBuilding()` had 3 hardcoded `.png` path suffixes for the building textures. Converting those 9 textures to WebP without updating these 3 strings would have 404'd and made the buildings disappear. Updated `.png` → `.webp` in those 3 template literals only — nothing else in Engine.js touched; the full engine rewrite still happens in Milestones 2-4 as planned.

**A real bug caught during verification, not before shipping it.** My first FOV-solver implementation used `distance = rig.distanceBehind + FRAMING.lookAheadZ` (~52-53 units) as the reference distance for the play-box fit. Sanity-checking this against the actual device matrix showed EVERY aspect ratio hit the 35° floor — the solver wasn't responding to screen shape at all, just returning the same fixed angle regardless of device, which would have been barely different from the original bug. Root cause: at ~52 units away, an 8×6 unit box subtends a tiny angle no matter the aspect ratio, so the floor clamp was always binding. Fixed by re-deriving what `lookAheadZ` actually is: a **spawning-rule constant** (nothing spawns closer than 45 units — Milestone 5's job), not a camera input — lane width only shrinks (in angular terms) at any distance beyond the near field, so a FOV that frames the box correctly at the player's own position automatically frames it at any farther distance too. Changed the solver to use `distance = rig.distanceBehind` only.

That fix then exposed a second, genuine problem: fitting an 8-unit-wide box from 7 units away on a narrow phone (aspect ~0.45) requires a ~96-102° FOV — well past any sane ceiling. This is real optics, not a bug: close + narrow + wide-box is a hard combination. Fixed by increasing the portrait rig's `distanceBehind` from 7 to 13 (with height raised from 6 to 9.5 to keep the viewing angle reasonably steep despite the extra distance) — verified this keeps every realistic phone aspect (down to ~0.45) at 68-69° FOV, comfortably under the 78° ceiling.

## Milestone 3 — World rewrite — ✅ DONE

**Goal:** Eliminate the ~0.67s chunk-recycle hitch (every recycle deep-cloned ~80 GLB objects: 30 railings, up to 50 trees, up to 2 buildings, up to 2 streetlights) and the resulting draw-call explosion, without changing what the world looks like or removing any visual element.

- [x] `src/game/world/TrackBuilder.js` — pure geometry/material factory for the track surface (base, 3 lanes, borders, trim) plus the asphalt canvas-texture generator moved from the old `WorldGenerator`.
- [x] `src/game/world/SceneryInstancer.js` — the actual fix. One global `InstancedMesh` pool per scenery variant (not per-chunk — per-chunk instancing was seriously considered but hand-computed to cost ~180 draw calls just for scenery due to buildings' 4-variant/low-count fan-out; global pools bring the same content down to 15). Every chunk's scenery slots get a **fixed** `(pool, instanceIndex)` assignment exactly once, at startup, never reallocated — only the world transform (chunk Z + per-recycle jitter) and visibility change afterward, so recycling costs zero allocation, just `Matrix4` composition into pre-existing buffers.
- [x] `src/game/world/WorldStreamer.js` — replaces `WorldGenerator.js` with an unchanged public API (`constructor(scene, textures, models)`, `setLevel()`, `update(delta)`, `.trackPool`, `.speed`). Coins/blockers stay as real per-chunk `Object3D` children (so `Engine.js`'s existing `checkCollisions()` traversal needed zero changes) but are now pooled — one coin + one blocker object per chunk, created once, reused via visibility toggling instead of recreated every recycle.
- [x] `Engine.js`: swapped `WorldGenerator` → `WorldStreamer` (one import line, one instantiation line), and replaced the old "repopulate all 15 chunks" trigger at the end of `loadAssets()` with a single `this.world.buildScenery()` call — scenery now builds once, when assets are ready, rather than being rebuilt piecemeal per chunk.
- [x] Deleted `WorldGenerator.js`. Dropped several pieces of pre-existing dead code encountered while rewriting this exact file: `interactables` array (write-only, never read anywhere — an actual unbounded memory leak in the original, since it grew every spawn and was never cleared), the cloud animation branch (`isCloud` was never assigned by any creation site), and the procedural tree/building fallback functions (`createBuildingGroup`, `createBuildingTexture`, `buildingMats`, `treeTrunkGeo`/`treeLeavesGeo`) — all made genuinely unreachable by the new design (scenery only builds once real models are loaded, so there's no "models not ready yet" case left to handle).

**A real discovery while inspecting the actual optimized GLBs (not assumed from the old code)**: the building models (`L_build_1/2/3`) ship 3 LOD (level-of-detail) variants per building — e.g. `"L_Build_1"` (2307 verts), `"L_Build_1_LOD1"` (1023 verts), `"L_Build_1_LOD2"` (221 verts) — all at identical transform. The old code's generic mesh traversal applied a material to every child mesh it found, meaning **all 3 LOD levels were being rendered simultaneously, stacked on top of each other**, for every building, this whole time. `SceneryInstancer` now picks only the highest-vertex-count (=LOD0) mesh per building variant. Also discovered: streetlights ship 2 alternative arm styles (`"Single_arm"`, `"Double_arm"`) as two separate nodes — `Engine.js`'s existing `setupStreetlight()` was already correctly extracting just `"Single_arm"` before storing it, so `SceneryInstancer` receives an already-clean single mesh for that one and needed no special-casing.

- [x] `src/game/systems/InputManager.js` — keyboard (arrows/WASD/space) + touch (swipe with a screen-proportional distance threshold + max-duration, tap-zone fallback for lane changes). Poll-based: DOM events queue a request, `Player.update()` consumes the queue once/frame. Ignores keydown while a form field has focus (Registration screen). Exposes `.scheme` ('keyboard'/'touch'/'both') for Milestone 8's UI hints to consume later.
- [x] `Player.js` moved to `src/game/entities/Player.js`, rewritten around an explicit `movementState` machine (`RUNNING`/`JUMPING`/`SLIDING`). `isHit` is a separate overlay flag, not a 4th state — matches the original's actual behavior (a blocker hit locks input and flashes red but never interrupted an in-progress jump/slide). `writeHitboxBox3()` exposes the state-driven capsule (2.0 running/jumping, 0.9 sliding) into a reused `Box3`. Slide is now a real timed state (700ms + 100ms recovery cooldown) instead of a `setTimeout` mutating the transform directly; hit-reaction's red-flash clear moved from `setTimeout` to the same per-frame timer pattern, for the same reason (a `setTimeout` doesn't respect the game's own delta-time or pause state).
- [x] `src/game/systems/CollisionSystem.js` replaces `Engine.js`'s per-render-frame `checkCollisions()`. Fixed 1/60s accumulator (capped steps/frame) driving a swept Z-interval check per interactable — world scroll is uniform-velocity within a frame, so linearly interpolating each item's z between its last-checked and current position exactly reconstructs the true intermediate path; each fixed step checks its own sub-span against the player's current hitbox. Also fixed a `new THREE.Vector3()`-per-item-per-frame allocation that existed in the original `checkCollisions()`.
- [x] `Engine.js`: constructs `InputManager`/`CollisionSystem`, passes `InputManager` into `Player`, `checkCollisions()` method deleted entirely (replaced by a `collisionSystem.update()` call gated on `mode === 'PLAYING'`, matching the original's exact gating). Input is captured regardless of mode but only *acted on* during PLAYING — physics/timers keep running unconditionally so an in-progress jump/slide resolves naturally instead of freezing mid-air on a mode switch.
- [x] Deleted `Player.js` (old top-level location) and the dead `this.currentAction` reference it had (declared but never actually assigned, making the original's "pause run animation during jump" comment describe code that could never execute) — now properly tracked so that behavior actually works.

**Three real, substantive bugs found and fixed during verification** — none were assumptions or guesses, all confirmed by running the actual shipped code:

1. **Jump apex was framerate-dependent.** The initial implementation used step-by-step (semi-implicit Euler) integration, matching the original's style. Numerically measured against the real code: apex landed at 1.89 (5.3% low) at a real 60fps, and 1.69 (15.3% low) at 20fps — meaning a player on a struggling phone would get a measurably shorter jump than one on a smooth device for the identical button press, silently varying difficulty by hardware in exactly the way Milestone 2's `lookAheadZ` fairness principle was built to prevent. Fixed by switching to the analytic closed-form position `y(t) = v0*t + 0.5*g*t²`, which gives the exact same apex regardless of frame rate or timestep — verified via the real `Player.js` to land at exactly 2.0000 at both 240fps (test resolution) and by formula at any other rate.
2. **Buffered input consumed one frame late.** `update()` originally processed input before resolving state timers, so a jump buffered during a slide wasn't consumed until the frame *after* the slide's timer actually expired, not the same frame — wasting a frame of the buffer window every time. Fixed by reordering: state-timer resolution now runs before input processing each frame.
3. **`SLIDE_RECOVERY_MS` (150) was mathematically incompatible with `INPUT_BUFFER_MS` (120).** Worked through the algebra: for a buffered action to survive a recovery cooldown, `INPUT_BUFFER_MS >= remaining-slide-time + SLIDE_RECOVERY_MS` must hold for whatever remaining-slide-time was true at press-time -- since remaining-slide-time >= 0 always, this requires `INPUT_BUFFER_MS >= SLIDE_RECOVERY_MS`, which was violated (120 < 150). In practice: a jump/slide buffered at *any* point during a slide would always have already expired by the time the recovery cooldown cleared, silently defeating the buffering feature specifically for the slide→jump/slide chain, no matter when during the slide the player pressed. Fixed by tuning `SLIDE_RECOVERY_MS` down to 100 (still a real, perceptible anti-spam pause, now safely under the buffer window).

**Verification performed** (all against the actual shipped modules, imported directly into a Node smoke test with minimal `window`/`document`/`fetch`/`Request` stubs — not a reimplementation):

2. **Jump apex**: measured by stepping the real `Player.update()` loop from `_startJump()` to landing — lands at exactly 2.0000, matches `jumpForce²/(2·|gravity|)` to floating-point precision.
3. **State-driven hitbox**: `writeHitboxBox3()` checked directly for all three states — RUNNING/JUMPING both 2.0 (JUMPING's bottom confirmed to track `mesh.position.y`, i.e. "raised by jump arc" rather than a separately-sized box), SLIDING is 0.9 and its top (0.9) confirmed ≤ DRONE_LOW's 1.1 bottom. ### Interactive tutorial — design notes
A real constraint of the chunk-pool architecture (Milestones 3/5) shaped this, discovered empirically rather than assumed: **every one of the 15 pooled chunks starts completely empty and only ever gets real content once it individually reaches the recycle threshold** — verified by instrumenting the actual `WorldStreamer` in a Node script rather than reading the code and guessing. For the pool's farther chunks that threshold is hundreds of world units away, and a pattern dealt through the NORMAL recycle path always starts ~poolSize×trackLength (~270 units) from the player — even at a generous slowdown, far more than "~15 seconds" can wait for.

The fix: `WorldStreamer.startTutorial()` seeds 3 ALREADY-CLOSE, evenly-spaced chunks (indices 3/6/9, at world z = -50/-110/-170 — chunk 3 lands close to `FRAMING.lookAheadZ` (45), the same "nothing spawns closer than this" fairness distance normal gameplay already guarantees) **directly**, bypassing the wait-for-natural-recycle path entirely. This is what actually makes a fast tutorial possible under this architecture; verified numerically that the 3rd (farthest) seeded obstacle fully arrives and passes the player within the slowdown's own 200-unit window (at the 0.45× slowed speed, ~14.8s total — a genuine match to "~15 seconds," not just a label).

**"Waits for the correct input" is satisfied by a generous slowdown, not a literal world-freeze.** A hard freeze would need `WorldStreamer.speed = 0`, which stops ALL chunk movement — meaning chunk recycling, the difficulty ramp, and coin/obstacle motion would all need to suspend and cleanly resume on release. That's real added risk to three already-verified systems (Milestones 3/5/6) for a booth-demo tutorial; the 0.45× slowdown gives several real seconds of reaction time per obstacle, which is the practical goal "waits for input" is actually after, at a fraction of the risk. Documented explicitly as a scope decision, not a shortfall.

Other tutorial mechanics:
- `SpawnDirector.selectPattern()` gained an optional `forcedId` parameter (default `null` — every existing call site is byte-for-byte unchanged) that resolves one SPECIFIC pattern through the exact same `build()` + `checkSolvability()` path as random selection, rather than an unverified shortcut.
- Any OTHER chunk that reaches its natural recycle threshold DURING the tutorial's window is forced to the always-safe `empty-coin-trail` filler (obstacle-free, but still deals a normal coin trail) instead of a random pattern — a stray, un-telegraphed obstacle appearing while the player is still learning would be confusing and unfair.
- Every tutorial-seeded obstacle is marked `isTutorial: true` (threaded through `WorldStreamer` → `CollisionSystem`'s blocker payload → `App.vue`), which skips the life cost (but keeps the full normal popup/flash/audio feedback, so the cause-and-effect still teaches something) for a miss on one of the 3 seeded practice obstacles — 3 unlucky misses in a row on a visitor's very first-ever attempt at the controls shouldn't be able to end the run before it really starts.
- Triggered once per RUN (not once per Level-1 VISIT) via `Engine._tutorialShownThisRun`, reset only by `resetRun()` (i.e. `quitToLobby()`) — a mid-run "Restart Level" from `PauseMenu` on Level 1 correctly does NOT re-show it, since it was already shown moments ago in the same run.
- A single combined HUD banner (not 3 sequential contextual prompts, which would need precisely tracking which specific seeded obstacle the player is nearest to — a real simplification, documented as such) shown for the whole slowed window.

### 1. Missing scenery — ROOT CAUSE FOUND, FIX WRITTEN, PENDING USER VISUAL CONFIRMATION

**Root cause**: Milestone 1's pipeline (`optimizeAssets.js`) Draco-compresses every environment/tree/building `.glb`. `Engine.js`'s `loadAssets()` creates a `GLTFLoader` but never attached a `DRACOLoader` to it. Every optimized environment GLB therefore failed to parse with `THREE.GLTFLoader: No DRACOLoader instance provided.` — caught silently by each `loadModel`/`loadBuilding` call's own `try/catch`, which only `console.error()`s. Nothing ever surfaced this visually; the scene just built with an empty scenery-model map, so `SceneryInstancer` (working exactly as designed — verified by re-reading it end to end this session) had nothing to pool. Milestone 7's character models load fine because they were exported via `GLTFExporter` with no Draco compression at all — a different pipeline — which is why the player character was the only thing ever visible.

Verified two ways this session, not assumed from reading code: (1) `curl` against the actual dev server confirmed every environment GLB is served correctly (HTTP 200, correct size/content-type) — this was never a file-serving problem; (2) parsed the real optimized GLBs in Node with the exact `GLTFLoader` code path `Engine.js` uses — reproduced the exact `No DRACOLoader instance provided` error for all 8 files, confirming the diagnosis against the real code.

**Fix**: copied the Draco decoder (`draco_decoder.js`/`.wasm`, `draco_wasm_wrapper.js`) into `public/draco/`, served locally rather than from three.js's default gstatic.com CDN (same "never depend on a remote resource the booth wifi might not reach" rule as the SoundHelix removal in Milestone 9). Wired a `DRACOLoader` (`setDecoderPath("/draco/")`) into `Engine.js`'s `GLTFLoader` — the actual fix — and, as future-proofing, into `CharacterLoader.js`'s too (today's placeholder characters aren't Draco-compressed, but a real licensed replacement might be). Re-ran the Node parse after the fix: the "No DRACOLoader" error is completely gone for all 8 files.

**What to check in your browser**: hard-refresh `localhost:5173` (Ctrl+Shift+R, to bypass any cached module) and start a run. You should see trees (maple/poplar/white poplar), buildings, metal railings, and streetlight poles along the road — not just the character on an empty road.
**If it's still broken**: F12 → Console tab, look for any line containing `GLTFLoader` or `DRACOLoader`. Screenshot it if you see one — that means the fix didn't fully take.

### 2. "Water-like" road surface — ROOT CAUSE FOUND, FIX WRITTEN, PENDING USER VISUAL CONFIRMATION

Found incidentally while investigating #1, directly tied to the visual-quality complaint. `scripts/downloadAssets.js` downloaded three.js's own `waternormals.jpg` (a literal water-ripple texture) and renamed it `asphalt_normal.jpg` — an inherited, unexamined leftover from the pre-rewrite original code. ### 7. No touch/swipe controls on mobile — ✅ FIXED, CONFIRMED BY USER ON A REAL DEVICE

**Investigation**: traced the full path — `InputManager` binds `touchstart`/`touchend` to `targetElement` (`#game-canvas-container`, confirmed correct per `Engine.js`'s constructor and the plan's own requirement, NOT `window`); `Player.js`'s `_processInput()` correctly calls `consumeLaneRequests()`/`consumeBuffered()` every frame when enabled; `SWIPE` thresholds in `GameConfig.js` (4% of screen width or 24px floor, ≤400ms) are reasonable, not misconfigured. All of this matches the plan and works logically — but **could not be reproduced or root-caused with certainty from this sandbox**, since there's no real touch-capable device or working browser automation available here (same standing limitation as every visual check this whole escalation). This is a best-reasoned fix for the most likely explanation, not a confirmed root cause the way the scenery/tree bugs were.

**Most likely explanation identified**: the touch listeners were registered `{ passive: true }`, which means they can never call `preventDefault()`. `App.vue`'s `.app-container { touch-action: none }` is an ANCESTOR-level CSS restriction that should, per spec, prevent the browser from hijacking a swipe as its own gesture (page scroll, pull-to-refresh, edge-swipe-back) — but relies on every mobile browser's touch-action ancestor-propagation being spec-perfect across a `position:absolute` boundary, which isn't guaranteed. If a real phone's browser DOES take over mid-gesture, it fires `touchcancel` instead of `touchend` — which this class didn't even listen for — so the swipe vanishes with zero lane-change/jump/slide queued and no visible error. This matches "all four directions do nothing" better than a threshold/config bug would (a bad threshold would misfire or need unreasonably large swipes, not fail 100% of the time).

**Fix** (`src/game/systems/InputManager.js`): listeners switched to `{ passive: false }`; `_onTouchStart` now calls `e.preventDefault()` directly (the same defense-in-depth browsers themselves recommend for canvas/game surfaces, not dependent on CSS propagation quirks); added a `touchmove` listener (`preventDefault()` only while a tracked swipe is in progress) and a `touchcancel` listener (clears in-progress swipe state cleanly instead of leaking into a later unrelated touch). Also added `touch-action: none` directly onto `#game-canvas-container canvas` in `style.css` as a second, redundant layer of the same protection.

**Verification performed**: real class exercised through a Node harness with a fake DOM target implementing real `addEventListener`/`removeEventListener` semantics (not a reimplementation) — confirmed all 4 swipe directions correctly queue/buffer the right action, `touchstart`/`touchmove` correctly call `preventDefault()` (and `touchmove` correctly does NOT when no swipe is being tracked), `touchcancel` correctly clears state without misfiring on a later unrelated touch, and `dispose()` removes all 4 listener types. `npm run build` succeeds cleanly. **This proves the logic is internally correct — it does NOT prove this was the actual root cause of the real-device symptom**, since a Node harness can't reproduce a real mobile browser's native gesture-takeover behavior.

**User re-tested**: still broken, but with a new and different symptom than before — swiped fast right after game start, the FIRST swipe correctly registered (lane changed left), then every touch after that did nothing. This is meaningfully different from "no swipe ever works": it points away from the "browser hijacks the gesture, nothing ever reaches the listener" theory (that would fail from the very first attempt, not work once then stop) and toward something STATE-related — either the touch events genuinely stop being delivered to the element after that point (a DOM/coverage/z-index issue that appears only after some UI state changes, e.g. a popup or the tutorial banner), or events keep arriving but the swipe-interpretation logic gets stuck (e.g. `_touchStart` left in a bad state). Re-read `CollisionSystem.js` in full to rule out one specific hypothesis (a hit-lock loop where `Player.isHit` never clears because the same obstacle keeps re-triggering `takeHit()` every frame, permanently blocking `_processInput()`) — ruled out: `_reportHit()` sets `item.visible = false` immediately and invisible items are skipped entirely at the top of `_checkItem()`, so a single obstacle provably cannot hit the player more than once per activation.

**Rather than guess a third time, instrumented the real code with temporary diagnostics** so the next test produces hard data instead of another ambiguous description:
- `InputManager.js` now tracks `debugCounts` (touchstart/touchmove/touchend/touchcancel counters) and `lastSwipe` (the exact diffX/diffY/distance/duration/threshold/result of the most recently completed gesture, including *why* it was or wasn't recognized as a swipe).
- `GameHUD.vue` polls these every frame (same rAF pattern as the power-up radial timer) and renders them in a small, clearly-labeled, `pointer-events: none` readout in the bottom-left corner during gameplay -- explicitly temporary, to be deleted the moment this bug is found (every added block is commented "TEMPORARY ... delete this once ... resolved" so it can't be missed later).
- Verified via the same Node harness as before (rebuilt against the now-instrumented class) that all 4 swipe directions, `preventDefault()` scoping, `touchcancel` handling, and `dispose()` still behave identically -- the debug counters are purely additive, they don't change any existing control flow. `npm run build` succeeds cleanly (94 modules).

**User reported back the critical data point**: the debug counters read `0 0 0 0` the entire time -- meaning touch events NEVER reach `InputManager` at all, not even once. This is definitive: it rules out the swipe-interpretation-logic theory entirely (there's nothing to interpret if no event ever arrives) and confirms something is covering the canvas and swallowing every touch before it gets there.

**ROOT CAUSE FOUND** (via direct inspection of the actual COMPILED CSS, not more guessing): `GameHUD.vue`'s root element (`.hud-container`, which covers the entire screen at `width:100%;height:100%`) declares `pointer-events: none` specifically so touches on the open play area fall through to the canvas underneath -- ONLY specific children like the pause/music buttons (`.utility-group { pointer-events: auto }`) opt back in. But `App.vue`'s `.ui-layer > * { pointer-events: auto }` (which exists to make every OTHER screen's root clickable by default) ends up with the EXACT SAME CSS specificity as `.hud-container`'s own rule once Vue's scoped-style attributes are compiled in (both resolve to one class + one attribute selector -- confirmed by inspecting `dist/assets/*.css` directly). A tie between equally-specific rules is broken by SOURCE ORDER, and App.vue's rule happened to land later in the bundle -- so `.hud-container` was silently computing to `pointer-events: auto` despite its own declaration, meaning the ENTIRE full-screen HUD (not just its buttons) was invisibly capturing every touch on the whole screen before it could ever reach the canvas. This is exactly why the debug counters read all zeros: the touches were real, they just never got past the invisible HUD layer sitting on top of the game.

**Fix**: `.hud-container { pointer-events: none !important; }` in `GameHUD.vue`. `!important` unconditionally wins regardless of future source-order shuffling from unrelated edits -- this property is exactly the kind of thing a component needs final, unambiguous control over for its own root, independent of a generic ancestor default. Confirmed this doesn't affect `.utility-group`'s buttons: a rule that directly matches an element (even without `!important`) determines that element's own value outright, it isn't in competition with an ancestor's `!important` declaration at all -- verified via the compiled CSS that `.hud-container[data-v-xxx]{...pointer-events:none!important}` is now present, and confirmed no other component has this same conflict (grepped every `pointer-events: none` in `src/ui/` -- `.hud-container` is the only case where it's declared on a screen's OWN ROOT that's also a direct child of `.ui-layer`; every other usage is on a nested, non-root element `.ui-layer > *` never touches).

**A second, much larger bug found while investigating the mobile-popup-visibility complaint below**: fixing that complaint required adding a NEW `:global(html[data-size-class="..."]) .someClass` CSS rule (the same pattern already used throughout `Landing.vue`/`GameHUD.vue`/`RegistrationForm.vue` for phone-specific overrides since Milestone 8) -- and inspecting the compiled output to verify it worked revealed it **doesn't compile the way this codebase assumed**. Confirmed directly against the real `@vue/compiler-sfc` (a minimal reproduction, not a guess): `:global(A) B` compiles to just `A { ... }`, silently DROPPING `B` entirely. This means **every phone-landscape/phone-portrait responsive override in this entire codebase -- ~34 rules across all 3 files, including the Lobby's short-landscape layout, the Registration form's keyboard-open layout, and TV attract mode -- has been a complete no-op since Milestone 8.** Nobody caught this because it required a real device in a real "phone-landscape"/"tv" size class to ever surface, which this sandbox could never test. Fixed all ~34 occurrences to the correct whole-selector form (`:global(A B)`, wrapping BOTH the ancestor and descendant together in one call). Verified via a script scanning the compiled `dist/` CSS for every `data-size-class` rule: 0 rules missing their descendant class, down from all of them.

**User confirmed on their real phone**: swiping repeatedly now works correctly (no longer stops after the first swipe). The temporary debug instrumentation (`InputManager.js`'s `debugCounts`/`lastSwipe`, `GameHUD.vue`'s `touchDebug` state + `.touch-debug` template block/CSS) has been fully removed now that it did its job -- confirmed via grep that zero references remain anywhere in `src/`, and `npm run build` still succeeds cleanly (94 modules) after removal.

- **`lookAheadZ`'s "minimum reaction distance" guarantee is satisfied structurally, not by an active per-spawn check** — Milestone 5's `SpawnDirector` never actively measures distance-to-player before placing a pattern; it relies on the chunk-recycle architecture itself (new content only ever instantiates when a chunk recycles to the back of the 15×20 pool, ~270 units from the player, always far beyond even a heavily speed-ramped `lookAheadZ`). `WorldStreamer`'s constructor asserts pool depth against `spawnDirector.dynamicLookAheadZ()` at startup specifically so this claim stays checkable if `poolSize`/`trackLength` or the ramp multipliers are ever changed later — don't remove that check without re-verifying the margin by hand.
- **`MIN_OBSTACLE_GAP_SECONDS` (0.15) is deliberately modest, not a full reaction-time window** — it's a speed-adaptive safety valve that excludes a tightly-spaced authored combo only once speed climbs high enough to make it genuinely unfair, not a blanket per-obstacle-pair reaction-time requirement. If a future milestone authors a new pattern with obstacles closer than ~2 units apart at level-1 speed, it may get excluded even at the easiest difficulty — widen its z-offsets (as `gauntlet-three` needed) rather than lowering this constant further.
- **Obstacle visual complexity is capped at 3-4 meshes/instance by design** (`ObstacleFactory`'s drones use one spinning rotor-ring mesh, not 4 separate arm+rotor pairs) — multiple obstacles can be visible simultaneously (`double-drone-*`, `gauntlet-three`), so if Milestone 9's juice pass wants richer obstacle visuals, budget mesh count per instance carefully against the ~15-draw-call scenery target Milestone 3 established, the same way this milestone did.
- **Pain-point (blocker) naming is independent of obstacle visual/physical type** — any of the 4 `OBSTACLE_TYPES` can carry any pain point from the level's blocker list, picked randomly with replacement each time a slot activates (pain points are meant to recur often, unlike coins which are collected without replacement). If Milestone 6 or 9 wants a specific pain point tied to a specific obstacle shape, that's a new constraint, not something the current data model expresses.
- **Portrait camera rig is tuned for math correctness, not yet for feel** — `CAMERA_RIGS.portrait` in `GameConfig.js` (height=9.5, distanceBehind=13) was derived specifically to keep the required FOV under the 78° ceiling at real phone aspect ratios. This is a reasonable starting point but hasn't been eyeballed in a real browser (sandbox limitation, see Milestone 1's note) — if the user reports the portrait camera feels too far/high, that's the first place to look, and there's real math margin to bring it closer (verified safe down to ~distance=11 before the ceiling binds at the narrowest realistic phone aspect).
- **All 4 characters share ONE skeleton using real Mixamo bone names** (`mixamorigHips`, `mixamorigSpine`, `mixamorigSpine2`, `mixamorigNeck`, `mixamorigHead`, `mixamorigLeftShoulder/Arm/ForeArm/Hand` ×2 sides, `mixamorigLeftUpLeg/Leg/Foot` ×2 sides — 19 bones total, see `scripts/generateCharacterAssets.js`'s `BONE_DEFS`) — this was a deliberate choice, not just a naming convenience: a real licensed Mixamo export uses exactly these strings, so this is what actually makes the "drop in a real model later with zero code changes" promise in `GameConfig.js`'s `CHARACTERS` comment true. **If a future milestone or a real character asset introduces a DIFFERENT bone naming scheme** (e.g. a non-Mixamo rig), `animations.glb`'s clips won't retarget onto it — either re-export `animations.glb` against the new names, or rename the new model's bones to match; don't assume any rig "just works."
- **The shared animation clips are rotation-only by design (no position/translation tracks)** — found and fixed during this milestone's own verification, not a stylistic default: the 4 characters have different scales/proportions (chibi anime characters are ~0.78-0.8× scale with enlarged heads), so a position keyframe authored against one character's bind pose (e.g. "raise the hip by 0.05 units") would land at the wrong relative height on a different-proportioned character. Quaternion rotations are proportion-independent and were verified to retarget correctly across both the tallest (`male_suit`, scale 1.0) and shortest (`anime_wizard`, scale 0.78) characters using the literal same clip data. **If a future milestone (e.g. Milestone 9's landing-squash juice) wants to add a position-based keyframe to any shared clip**, it will look wrong on at least one of the 4 characters unless it's expressed as a fraction of that character's own height rather than an absolute offset — this is a real constraint on the shared-animation-library design, not an oversight to "just fix later" the easy way.
- **Jump/Slide no longer use `setAnimation()`'s crossfade** — they use a new `Player._playOneShot()` helper (plain independent fade-in/fade-out) instead, because `setAnimation()`'s `crossFadeFrom(..., warp=true)` measurably distorted the precise duration `AnimationAction.setDuration()` had just set (caught by Milestone 7's own verification script, not assumed) — warping is designed for syncing two looping cycle-based clips of different lengths (which is exactly what Idle↔Run still uses it for) and actively fights a short one-shot clip's intentionally-exact timing. **If a future milestone adds another one-shot reaction clip** (e.g. Milestone 9's Stumble-on-hit), use `_playOneShot()`, not `setAnimation()`.
- **`Player.setFacing(rotationY)` replaces Engine.js directly writing `player.model.rotation.y`** — introduced this milestone because `player.model` can now be swapped out entirely (`setCharacter()`), and anything written straight onto the old model reference would silently vanish on the next swap. **Any future code that needs to orient the player model must go through `setFacing()`**, not touch `.model.rotation.y` directly, or it will quietly stop working the first time a character switch happens after that code runs.
- **`selectedCharacterId` lives in `App.vue`, not in `Landing.vue`/`CharacterSelect.vue`** — `Landing`/`CharacterSelect` fully unmount and remount every time `gameState` cycles back to `'LANDING'` (e.g. `quitToLobby()`, renamed from `restartGame()` in Milestone 8 — see below), so anything they own resets to that component's own default on every remount. `App.vue` is the only thing that persists for the whole session, so it's the only place that can remember a mid-session character pick across a restart. If a future milestone moves character selection somewhere else in the flow (e.g. a dedicated full-screen `CharacterSelect` state per the original plan wording), keep the "authoritative selection lives in the thing that doesn't remount" rule.
- **`scripts/generateCharacterAssets.js`'s Node `FileReader` polyfill is reusable** — any FUTURE script that needs `three.js`'s `GLTFExporter` to produce a binary `.glb` from plain Node (not a browser) will hit the same `FileReader is not defined` error; the fix (bridge Node's native `Blob.arrayBuffer()` to `FileReader`'s callback shape, ~10 lines) is already written and battle-tested in that file — copy the `NodeFileReader` class rather than rediscovering the problem.
- **`App.vue`'s `restartGame()` was renamed `quitToLobby()` in Milestone 8** and is now shared by both `GameOver`'s retry AND `PauseMenu`'s Quit (previously only the former existed). If any future code searches for `restartGame`, it's gone — same full-run-reset behavior, new name, one more caller.
- **Any future full-screen overlay that can appear ALONGSIDE another mounted screen (not instead of it) MUST set its own `position: absolute; inset: 0`** — found and fixed in Milestone 8: every top-level screen component's root before `PauseMenu.vue` only ever appeared ALONE (the `v-else-if` chain + `<Transition>` in `App.vue` guarantee exclusivity), so a plain `width:100%;height:100%` block with no explicit `position` was never actually tested against having a sibling. Two such siblings stack vertically in normal document flow instead of overlaying, silently pushing the second one below the visible viewport (then clipping it via `.app-container`'s `overflow:hidden`). `PauseMenu.vue` is the first and (so far) only component that needs this; if Milestone 9 or later adds another simultaneous-overlay UI (e.g. a toast/announcement layer above gameplay), give it the same explicit positioning from the start.
- **GSAP tweens and Vue `:style`/`:class` bindings must never target the same CSS property on the same element** — found and fixed in Milestone 8 (`GameHUD.vue`'s progress bar fill had both). Vue re-applies template bindings on every re-render triggered by ANY reactive dependency changing, not just the one the binding reads from, so it will stomp on a GSAP tween's in-progress inline style. Pick one owner per animated property: either a plain CSS `transition` + Vue binding, or a `ref` + GSAP `.to()`, never both on the same element/property pair.
- **Any HUD display value that's a WHOLE-RUN stat (persists across levels) must initialize from the current prop value, not a hardcoded 0/default, when the displaying component remounts every level** — found and fixed in Milestone 8 (`GameHUD.vue`'s score counter). `GameHUD.vue` itself remounts fresh each level (it's in `App.vue`'s `v-else-if` chain), but `gameStats.score` does not reset per level, so a hardcoded-0 initial value shows "0" on every level-2+ mount until the next coin. `levelFeaturesCollected` doesn't have this problem only because IT genuinely does reset to 0 every level — don't assume every counter is safe to zero-initialize just because one of them is.
- **A per-level "Restart Level" feature must clear that level's own features from the run-wide `featuresCollected` list, not just zero the level's progress counter** — found and fixed in Milestone 8. `handleCollision`'s coin-dedup check (`!gameStats.featuresCollected.some(f => f.name === hit.name)`) is keyed across the WHOLE RUN, not the current level; resetting only `levelFeaturesCollected` to 0 without also removing the current level's own entries from `featuresCollected` makes the restarted level's own coins silently refuse to re-count, so `requiredCount` becomes permanently unreachable. If a future milestone adds another "retry this level" entry point, apply the same `featuresCollected.filter(...)` step.
- **EVERY one of `WorldStreamer`'s 15 pooled chunks starts completely empty and only gets real content once it individually reaches the recycle threshold** — discovered empirically in Milestone 9 (instrumented the real `WorldStreamer` in a Node script; NOT assumed from reading the code), and it's the reason the interactive tutorial couldn't just wait for natural recycles to happen. `setLevel()`/the constructor never call `_refreshChunkContent()` directly for the initial pool; content only ever appears via the per-chunk recycle branch inside `update()`. Concretely: chunk `i` starts at world z = `activeZ - i*trackLength` and stays exactly that (empty) until IT crosses `z > activeZ + trackLength`, which for the pool's farther chunks is hundreds of units away. **If a future milestone wants ANYTHING to appear near the player at the very start of a level** (another tutorial-like feature, a "first coin within 2 seconds" guarantee, etc.), don't rely on the normal recycle path for it — either seed a close chunk directly (`WorldStreamer.startTutorial()`'s pattern) or accept that the natural first-content delay is real and roughly a few seconds, not instantaneous.
- **`Engine.animate()`'s system update order is now load-bearing, not arbitrary** — `effectsSystem.update(delta)` specifically runs AFTER `collisionSystem.update()`, not before, because a coin-hit's particle burst is triggered synchronously from within `collisionSystem`'s `onHit` callback, and `EffectsSystem.burst()` only records state (position/velocity/life) — matrices are written on the NEXT `update()` call. Found by a Node script that checked the burst's actual matrix state immediately after triggering it and caught it still zero-scale (one frame late) with the old order. **If a future milestone adds another system whose `update()` needs to reflect a hit-triggered event THIS SAME FRAME**, it needs to run after `collisionSystem.update()` too, not just anywhere convenient.
- **`AudioManager`'s two `.wav` files are genuine digital silence, not placeholder tones** — a deliberate choice (see `scripts/generateAudioAssets.js`'s own comment), matching the plan's literal "silent placeholder stubs" wording rather than a "more useful" but unrequested alternative (a placeholder tone risks being mistaken for an actual sound-design decision). `SFX_DURATIONS`/`MUSIC_LOOP_DURATION_SECONDS` in `GameConfig.js` are the only things that need to change when real (licensed) audio replaces these files — re-run `npm run audio:generate` is obsolete at that point, real files just get dropped in at the same URLs.
- **`isTutorial` threading (WorldStreamer → CollisionSystem → App.vue) is the established pattern for "this hit shouldn't count against the player"** — same shape as Milestone 6's `"shielded"` vs `"blocker"` outcome-reporting pattern (report the OUTCOME/CONTEXT through the payload, let the Vue-side authoritative counter decide what to do with it, rather than having the engine silently suppress anything). If a future milestone adds another practice/tutorial/grace-period mechanic, extend this flag rather than inventing a parallel one.
- **`TUTORIAL_CHUNK_INDICES` (`[3, 6, 9]` in `GameConfig.js`) is derived from `WorldStreamer`'s CURRENT pool geometry** (`activeZ=10`, `trackLength=20` → chunk `i` starts at world z = `10 - 20*i`) — chunk 3 lands at z=-50, deliberately close to `FRAMING.lookAheadZ` (45). **If `poolSize`, `trackLength`, or `activeZ` are ever retuned**, these indices (and `TUTORIAL_DISTANCE`, tuned so the 3rd seeded obstacle's own arrival happens within the slowdown window) need to be re-derived, not assumed to still land in the same place — re-run the kind of empirical instrumentation this milestone used to verify it (see the note above), don't just recompute by hand.
